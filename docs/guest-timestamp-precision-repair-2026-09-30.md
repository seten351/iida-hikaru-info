# ゲスト更新の日時精度修正・復旧（2026-09-30）

## 原因と修正

通常のAdmin出演更新が、変更しない`visibility_changed_at`をDrizzleから取得したJavaScriptの`Date`で再書き込みしていました。Postgresのマイクロ秒値`.138395`が、その往復でミリ秒値`.138`へ丸められました。`starts_at`にも同じ往復のリスクがありました。

`src/server/admin/write-service.ts`で、通常更新のSET対象からvisibility関連カラムを除外しました。出演日時・精度・日付も現在の入力表示と同じ場合はSET対象から除外します。非公開化・復元では従来どおりvisibility状態・変更日時を更新します。公開日時・主情報元の更新経路、競合検知、冪等性、提案・履歴は維持しています。通常更新のversion・updated_atは監査のため従来どおり更新します。スキーマ変更はありません。

## 検証

- 全マイグレーションを適用した隔離Postgres（PGlite）で、出演・公開・visibility・収集日時と既存情報元に6桁精度を設定し、`to_jsonb`の値で比較しました。
- ゲスト更新、既存主情報元の根拠再利用、追加根拠、Previewの読み取り専用性、再実行、version競合、通常題名更新、意図した出演日時変更、非公開化・復元を検証しました。
- 復旧用CLIは、異なるhash、Preview後の変更、version変更、復旧根拠欠落を拒否します。日時復旧後の監査書き込みを意図的に失敗させ、日時と新しい提案・履歴がすべてロールバックすることも検証しました。
- 本番の対象出演・既存提案・履歴・情報元を、日時文字列の精度を保って隔離DBへコピーしました。Preview、復旧、既存値・過去履歴の保持、冪等な再実行が通過しました。本番Neonのブランチは変更していません。
- `npm run test:guests`：31件、`npm run test:publication`：14件、Adminテスト：25件、計70件成功。lint、`tsc --noEmit`、buildも成功しました。
